# Campaign runtime and recovery

The authored short fixture is Monza → Monaco with fixed constructor/person identities, neutral cars, materialised presets and event conditions. Full-calendar mode remains unavailable. Source metadata records provenance; materialised source data with the supported `1.0.0` schema does not need the currently bundled data-version label. Effective preparation, practice, replay, simulation/randomness and scoring contracts must remain understood.

The campaign record reserves each event's deterministic weekend identity before creating it. Start and next-event activation intents are saved before their weekend actions. A returning host retries the same operation after an interrupted acknowledgement. Campaign writes use one-record storage CAS; independent coordinators refresh authority before private campaign controller operations.

Completed weekend classifications come only from persisted, replay-validated server results. The final Event Contribution and `season-complete` lifecycle are saved together. Duplicate commits and callbacks return the existing contribution; they do not award points twice. An understood older record already containing its final contribution receives a CAS lifecycle repair without changing its result or awards. No third event or next preparation is created. Constructors are the primary championship, Drivers secondary. Historical raw results, awards and cumulative report deltas remain available after completion.

Unsupported or malformed records return an actionable conflict. They are not deleted, replaced with an empty campaign or silently migrated into different simulation inputs. Preserve the saved record and use its compatible deployment or a known backup. A transient storage outage requests retry of the same operation.

## Ownership and control across weekends

Authenticated player membership and constructor assignments carry into the next weekend. A preparation return explicitly replaces that player's authorised devices while preserving setup and the sole Practice Assessment. During an active race a return on a new device revokes previous private grants immediately and saves a replacement grant for the next existing Race Phase boundary. It does not authorise mid-phase input or remove accepted decision locks. The replacement survives restart. AI takeover/reclaim remains the existing explicit, revisioned next-boundary operation; a new device grant does not cancel an accepted takeover.

Race AI modes, pending takeover/reclaim intents and race decision locks reset for each new weekend. The next preparation boundary completes a saved authenticated device return if the old race ended before another decision boundary. No private choices or pending race instructions are copied into next-event preparation. Qualifying-locked returns remain public-history membership until race boundary recovery is available.

Unclaimed teams receive the existing recorded automatic preparation. An assigned absent team blocks readiness until its player confirms or the host explicitly chooses **Host: use disclosed AI preparation**. This records `host-absent-ai` in public readiness and keeps ownership. Existing Practice Assessment is retained; the policy evaluates a final choice from that observation instead of rerolling practice. Already Final-Ready preparation and accepted qualifying locks are preserved. This preparation action does not silently grant permanent race AI control; the host may request the existing race takeover separately.

Public campaign/SignalR state contains calendar, readiness, championship standings and committed reports. Private setup, estimates and recommendations remain under current device assignment and privacy mode. A device identity from another campaign grants no access; old revision private subscriptions receive no future private updates after revocation.

Focused checks use `playwright.campaign-recovery.config.ts` and `tools/auth-emulator/firebase.campaign-recovery.json`; their integration folder is excluded from the default gallery. Automated emulators/browser checks establish correctness only. Household acceptance, larger fixture runs and storage/hosting measurements belong to ticket 05.
