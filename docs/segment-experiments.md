# Segment experiments

Run `dotnet run --project tools/SimulationRunner -- --suite track-passing --runs 20 --output reports/segment-track-passing`. Optional positional arguments `40 7` select the initial paired seed; distance stays 40 laps. The suite rejects fewer than 20 seeds and conflicting fixture or strategy overrides before writing reports.

The bounded suite runs two 90-second, 5000-metre layouts, two 22-car fields and five controls per combination: segmented difficulty 0/0.4/0.8, zero-noise difficulty 0.4, and aggregate difficulty 0.4. Both layouts integrate Speed/Cornering demand to 0.5/0.5. Their local demands, lengths and passing-zone visits differ. Equal-all has identical driver and car attributes; mixed-car-fit alternates straight/corner strengths and includes small base Pace differences. The first strength pair has equal clear-air lap pace. These coefficients are experimental hypotheses. Two independent cases run concurrently with immutable input snapshots; seeds within each case and published cases retain their declared order. Concurrency and report writing are separate from the simulation-only benchmark in ticket 10.

Both plans start on Medium. Baseline schedules every driver to Hard after phase 4; the alternative moves driver-06 to phase 3. Seeds correspond across plans and controls. Lap variation is 0.2 seconds, stop variation 0.6 seconds, estimate error 0.04, race form zero and passing variation one. The zero-noise control sets all these magnitudes to zero, including passing variation: its fixed threshold of 0.5 makes this suite's chances fail, exposing queues and failed opportunities without ordinary random passes. Blue flags remain explicit.

`track-passing-evidence.md` reports actual Overtake events, attempted encounters, traffic loss and BlueFlag events separately. Pit-cycle position changes are separate strategy outcomes. `track-passing-summary.json` publishes settings, fields, plans, seeds, model/randomness versions, all variability statistics and eligibility/distance groups. Each case has full comparison replay inputs and one paired seed's final event/diagnostic history; regenerate other histories with `--replay`. Generated reports stay ignored; the concise published evidence lives under `.scratch/segment-race-model/evidence/`.

The runner retains the shared pure SegmentSimulation physics seam. While executing this suite, repeated projection validation at every traffic comparison proved expensive enough to motivate caching each car's resolved free trajectory. Segment entry, phase decisions, tyre changes and lap transitions refresh it through the same seam; current distance, constrained speed and remaining horizon are derived from the current trajectory. Existing transition tests and byte-identical retained sample histories verify behavior. Ticket 10 measures runtime formally.

`--suite tyre-pit` runs 36 preselected cases on the same layouts and fields. Seven one-factor tyre settings (default plus low/high degradation, exhaustion and warm-up) compare driver-06's phase-4 Hard stop against an explicitly ineligible no-stop control. Two alternative stop windows (phase 3/5) compare against legal all-driver phase-4 stops. Results separate raw equal-distance payoff and eligibility-qualified strategy outcomes. Crossing histories identify the first post-stop matching lap which repays the Pit Loss; unrepaid seeds stay explicit. Target traffic loss and out-lap duration help inspect spatial sensitivity. The existing tyre curve and other coefficients are unchanged.

Run `dotnet run -c Release --project tools/SimulationRunner -- --suite tyre-pit --runs 20 --output reports/segment-tyre-pit`. Outputs `tyre-pit-evidence.md` and `tyre-pit-summary.json` follow the same replay/history conventions. Bounded settings are degradation 0.0125/0.025/0.05 per equivalent lap, exhaustion 0/15/30 seconds/lap and warm-up 0/0.8/2 seconds before compound multipliers. All selected cases and eligibility/distance groups are published; these are sensitivity controls rather than balance recommendations.

Both selected layouts have distance-weighted TyreDemand 1.0. The default exhaustion sweep reaches zero condition at the final crossing, so it supplies no useful exhausted running before the finish; neutral results leave exhaustion strength inconclusive. High degradation exercises earlier exhaustion, but this bounded suite avoids a full crossproduct. Published default fresh-stop controls are slower on average in all four layout/field cases. Higher degradation reverses that diagnostic payoff on the open mixed-car-fit layout; restricted queues retain much of the gain. These no-stop baselines are ineligible, so this finding does not establish a legal strategy advantage.

`--suite form-noise` runs 20 preselected cases: both layouts/fields with zero, form-only, lap-only, combined and combined-high profiles. Full form/lap ranges in seconds are 0/0, 0.4/0, 0/0.2, 0.4/0.2 and 0.8/0.4. Other variability channels are zeroed to isolate these modifiers; deterministic passing uses the existing fixed 0.5 threshold. Both plans remain legal: all-driver phase-4 Hard stops, with driver-06 moved to phase 3 in the alternative.

Run `dotnet run -c Release --project tools/SimulationRunner -- --suite form-noise --runs 20 --output reports/segment-form-noise`. `form-noise-evidence.md` and `form-noise-summary.json` distinguish diagnostic modifier persistence from elapsed-lap outcomes affected by tyres, traffic and Pit Loss. Each race pools adjacent modifier pairs from the same driver; removing driver race means isolates temporal variation. Undefined correlations stay null. Distributions summarize independent seeded races, with per-seed results and all eligibility/distance groups. The suite checks exact corresponding exogenous diagnostic scopes within paired plans and reports unmatched scopes. Persistent form belongs to one driver in one race; no shared team/field or across-weekend factor is introduced.
